# ADR-0008: Mobile app with Expo (React Native), sharing the API and types

- Status: Accepted
- Date: 2027-03-15

## Context

Phase 5 ships iOS and Android test builds (TestFlight and Google Play internal testing). One
part-time developer maintains the whole platform, so the app must reuse the TypeScript skills,
the API and the shared schemas instead of starting a second stack. Shoppers expect native
payments (Apple Pay, Google Pay), push notifications, biometric sign-in, links that open in the
app, scanning a barcode in a shop, and a catalog that still works on a poor connection.

## Decision

| Concern         | Choice                                                                                          |
| --------------- | ----------------------------------------------------------------------------------------------- |
| Framework       | Expo SDK 57 (React Native 0.86, Hermes, New Architecture), in the monorepo as `apps/mobile`     |
| Native projects | Continuous Native Generation: `ios/` and `android/` are generated by config plugins, not stored |
| Navigation      | Expo Router (file-based). Routes mirror the storefront's URLs, so web links map 1:1 to screens  |
| API access      | `@nixzora/api-client`: typed, no runtime dependencies, one shared token refresh at a time       |
| Types           | `@nixzora/validation` for request/response types and the address schema used to validate forms  |
| Server state    | TanStack Query; the catalog is persisted to disk (7 days) for offline browsing                  |
| Sign-in         | Same EdDSA access tokens; the refresh token is stored in Keychain/Keystore (this device only)   |
| Biometrics      | Optional lock: Face ID / Touch ID / fingerprint before the saved refresh token is used          |
| Payments        | Stripe PaymentSheet on the same PaymentIntent as the web (cards, Apple Pay, Google Pay)         |
| Push            | Expo push service (APNs + FCM behind one API); tokens stored per device in `push_devices`       |
| Links           | Custom scheme `nixzora://` plus universal links / App Links served by the storefront            |
| Scanning        | `expo-camera` barcode scanning (EAN-13/8, UPC-A/E, QR) + `GET /catalog/lookup`                  |
| Builds          | EAS Build and EAS Submit, three variants (development, preview, production) side by side        |

### Why not the alternatives

- **Separate Swift and Kotlin apps**: two more languages and codebases for one developer.
- **Flutter**: good, but nothing would be shared with the TypeScript API and web apps.
- **A web view around the storefront**: no native payments sheet, weak offline story, and the
  App Store rejects apps that are only a wrapped website (guideline 4.2).
- **Bare React Native without Expo**: we would own native upgrade work that config plugins and
  EAS do for us; Expo still allows custom native code when it is needed.

## Consequences

- The API gained only small, generic additions: barcode lookup, push device registration,
  order push notifications and self-service account deletion (an App Store requirement).
- Tokens never pass through the storefront's BFF on mobile; the app talks to the API directly
  with bearer tokens, which the API already supported.
- Store builds need accounts and credentials the project owner creates (Apple Developer
  Program, Google Play Console, Expo). Until then the app runs in development builds; see
  [the mobile release runbook](../runbooks/mobile-release.md).
- A web preview of the app (`expo start --web`) exists for quick checks and automated
  screenshots only; the real website stays the Next.js storefront.
